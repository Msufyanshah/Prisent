### TASK-037 — Fix `linkedin_person_id` Data Model (Split Combined Field)

**Day:** D11 | **Estimate:** 1h | **Depends on:** TASK-032b | **Status:** done

**WHAT:** Replace the `id|name` combined string currently written to
`linkedin_person_id` with two separate columns: `linkedin_person_id`
(bare `sub` only) and `linkedin_display_name` (human-readable name).

**WHY:** Root cause confirmed directly in code (`linkedin_auth.py:L104`):
`linkedin_person_id` was deliberately set to
`f"{profile.get('sub')}|{profile.get('name', 'Connected User')}"` so the
`/auth/linkedin/status` route could show a display name without a schema
change. `linkedin_publisher.py` then wrapped this raw value directly into
the author URN without parsing it, producing a malformed URN and a
real publish failure. This was not a mock-mode data leak (confirmed by
direct database query — no mock values exist in any real user record).
It's an undocumented, overloaded-column design that already caused one
bug and will cause the same class of bug again anywhere else this field
gets read without knowing about the "|" convention.

**HOW:**
1. Add `linkedin_display_name: str | None` column via migration
2. Update the OAuth callback (`linkedin_auth.py`) to write `sub` and
   `name` to their own columns separately
3. Update `/auth/linkedin/status` to read `linkedin_display_name`
   directly — remove the `.split("|")` parsing there
4. Update `linkedin_publisher.py`'s URN construction to use the now-clean
   `linkedin_person_id` directly — remove its split/parse workaround
5. One-time data migration: backfill the existing user's combined value
   (`KLvwf8M1aM|muhammad sufyan shah`) into the two new columns correctly

**ACCEPTANCE CRITERIA:**
- [ ] `linkedin_person_id` contains only the bare `sub`, everywhere it's
      written
- [ ] `linkedin_display_name` exists as its own column
- [ ] No remaining `.split("|")` logic anywhere in the codebase
- [ ] Existing user's data backfilled correctly, verified by query

### TASK-038 — Guard Mock Mode Against Non-Development Use

**Day:** D11 | **Estimate:** 1h | **Depends on:** TASK-021 | **Status:** done

**WHAT:** Ensure the `LINKEDIN_CLIENT_ID == "mock-id"` sandbox path in
`linkedin_oauth.py` cannot be reached in staging or production.

**WHY:** Mock mode currently short-circuits real LinkedIn OAuth whenever the
env var equals `"mock-id"`. This was essential for local development while
waiting on LinkedIn product approval, but if this code path is ever
reachable in a deployed environment, it would let anyone fake a LinkedIn
connection without ever touching LinkedIn's real API — a real security and
data-integrity risk once the product is public.

**HOW:**
```python
# In each of the three mock-mode checks in linkedin_oauth.py, add an
# explicit environment guard:
if settings.LINKEDIN_CLIENT_ID == "mock-id":
    if settings.ENV != "development":
        raise RuntimeError(
            "Mock LinkedIn mode is not permitted outside development"
        )
    return ...  # existing mock behavior
```

**ALSO IN SCOPE — found in real backend logs:**
- Startup banner currently reports `env: deployment`, not `development` or
  `production` — confirm the exact string value `ENV` is expected to hold,
  and make sure this guard's comparison matches it exactly. A mismatched
  string here means the guard silently never fires in either direction.
- Logs show `Skipping background task execution on server due to
  x-skip-execution header` firing on real `/generate` calls. Confirm
  where this header is read, whether any external client can set it, and
  if so, lock it down (e.g. only honored when `ENV == "development"`, same
  as the mock-mode guard above) — a public API that skips real processing
  on a client-supplied header is a separate but related risk surface.

**ACCEPTANCE CRITERIA:**
- [ ] Mock mode raises an explicit error if `ENV` is not `"development"`
- [ ] Confirm `ENV` is set correctly in both Railway (backend) and Vercel
      (frontend, if relevant) deployment configs, and matches the exact
      string this guard checks against
- [ ] Manually test: attempting mock mode with `ENV=production` locally
      fails loudly, not silently
- [ ] `x-skip-execution` header confirmed inert (or explicitly
      dev-only-guarded) in any non-development environment

### TASK-041 — Replace In-Memory Qdrant with a Persistent Instance

**Day:** D12 | **Estimate:** 1.5h | **Depends on:** TASK-039 | **Status:** todo

**WHAT:** Move off `QDRANT_URL=":memory:"` for any deployed environment —
use a hosted or persistent Qdrant instance instead.

**WHY:** In-memory mode was fine for local development, but it means voice
memory / semantic retrieval data is wiped on every backend restart. In
production, a Railway redeploy or crash would silently erase all indexed
voice memory. This directly undermines TASK-037's earlier fix (which made
the in-memory client a shared singleton) — that fix solved the crash, but
persistence across restarts is a separate, still-open problem.

**HOW:**
1. Provision a persistent Qdrant instance (Qdrant Cloud free tier, or a
   Railway-hosted Qdrant service)
2. Set `QDRANT_URL` in production to the real instance URL, not `:memory:`
3. Confirm existing seed/index logic still runs correctly against a real
   instance (not just the in-memory shortcut path)

**ACCEPTANCE CRITERIA:**
- [ ] Production `QDRANT_URL` points to a persistent instance
- [ ] Voice memory data survives a backend restart/redeploy in production
- [ ] Local development can still use `:memory:` for speed — this task
      only changes production/staging behavior

### TASK-043 — Enforce Persona Fidelity in Generated Content (No Fabrication, No Generic AI Tone)

**Day:** D13 | **Estimate:** 2h | **Depends on:** TASK-042 | **Status:** todo

**WHAT:** Review and constrain the writer/reviewer agent prompts to fix two
confirmed, related defects in generated posts: (1) fabricated claims not
sourced from persona data, and (2) generic AI-sounding tone that ignores
the user's stated `unique_differentiator`.

**WHY — two confirmed real-world examples:**

*Fabrication:* A published post included a specific, quantified claim
("slashed error rates by 25%") that was not sourced from any persona field
the user entered. Publishing fabricated professional claims under a real
person's LinkedIn identity is a credibility and trust risk.

*Generic tone / ignored differentiator:* A persona explicitly set
`unique_differentiator` to "Focus on concrete code examples and
measurable performance metrics rather than theoretical high-level
concepts," with pillar "AI Ethics." The actual generated post for that
pillar was entirely abstract — no code, no concrete metric, structured
around rhetorical questions ("who holds ultimate responsibility for an
autonomous agent's actions?") and generic LLM patterns ("Here's a
practical insight," "Consider X," rhetorical-question closers). The post
was topically on-pillar but ignored the differentiator entirely — this is
not a style nitpick, the differentiator field is functionally decorative
in the current generation flow.

**HOW:**
1. Review the writer agent's system prompt — confirm whether
   `unique_differentiator` is passed as a hard constraint or just
   background context
2. Add an explicit instruction: generated posts must concretely reflect
   `unique_differentiator` (e.g. if it demands code examples or metrics,
   the draft must contain at least one), not just stay topically aligned
   with `content_pillars`
3. Add an explicit no-fabrication constraint: posts may make general
   observations and arguments, but must not state specific numbers,
   named outcomes, or "our team did X" claims unless those specifics were
   present in the user's own persona input
4. Add a house-style constraint against generic LLM patterns identified
   in the examples above: no rhetorical-question closers as the default
   ending, no "Here's a practical insight" / "Consider X" template
   openers, vary structure between generations rather than reusing the
   same rhetorical shape every time
5. Update the reviewer agent to explicitly score/flag: differentiator
   adherence, presence of unverified specific claims, and generic-pattern
   phrasing — not just voice_match/hook_quality/clarity as currently scored

**ACCEPTANCE CRITERIA:**
- [ ] Writer agent prompt updated to treat `unique_differentiator` as a
      hard constraint, not ambient context
- [ ] Writer agent prompt updated with an explicit no-fabrication
      constraint
- [ ] Reviewer agent scores/flags differentiator adherence and unverified
      specific claims
- [ ] Manually generate 5 test posts against the same persona and confirm:
      each reflects the differentiator concretely, none introduce
      unsourced numbers/outcomes, and closings/openers aren't templated
      identically across all 5

### TASK-046 — Hashtag Generation Pipeline (Keyword-Extraction Based)

**Day:** D13 | **Estimate:** 3h | **Depends on:** TASK-032b | **Status:** todo

**WHAT:** A hashtag generation pipeline that extracts keywords from the
generated post's own content and turns them into 3-5 relevant LinkedIn
hashtags, with no user input required.

**WHY:** Confirmed real gap — no hashtag field exists today, and a real
published post confirmed zero hashtags in the output. Product wants
agent-driven hashtag decisions with no manual tagging required.

**ARCHITECTURE — revised from an earlier trend-aware design:**
An earlier version of this task used a web-search-backed "trend agent" to
pull real-time trending hashtags. That design was replaced by product
decision: a live search call on every generation introduces latency,
cost, and a caching-freshness tradeoff with no clean answer. The revised
design instead extracts keywords directly from the post's own generated
text — self-contained, no external calls, no staleness problem.

**Known tradeoff, accepted:** this approach produces hashtags that are
topically accurate to the post's actual content, but has no signal about
which tags are currently high-reach/trending. If trend-awareness becomes
a priority later, it should be scoped as a separate, standalone future
task — not re-added to this pipeline by default.

**SCOPE NOTE:** LinkedIn only. Platform passed as an explicit parameter
so X/Facebook rules can be added later without restructuring.

**HOW:**
1. `get_persona_context(user_id)` — plain DB read: `content_pillars`,
   `niche`, `preferred_hashtags` (optional hint)
2. `keyword_extraction_agent` — reasoning agent call: given the generated
   post's full text and persona context, extract the 4-6 most important
   topical keywords/phrases actually present in the post (not invented,
   not generic — must be traceable to something the post actually says)
3. `normalize_and_merge(keywords, preferred_hashtags)` — deterministic
   code: convert extracted keywords into hashtag-cased format
   (`decision trees` → `#DecisionTrees`), merge with any user-set
   `preferred_hashtags`, dedupe
4. `hashtag_selector_agent` — reasoning agent call: given the candidate
   list, persona context, and platform rules, select the final 3-5 tags
   — relevance over generic reach, placed at the end of the post, not
   inline
5. Hand the final tag list to the writer agent to append to the
   generated post

**ACCEPTANCE CRITERIA:**
- [ ] Persona schema includes optional `preferred_hashtags` hint field
- [ ] Keyword extraction agent produces keywords traceable to the actual
      post text (not fabricated/generic)
- [ ] Final output is 3-5 relevant tags per post, placed at the end
- [ ] Reviewer agent flags 0-hashtag posts or clearly irrelevant/
      generic-only tag selection
- [ ] Generate 5 posts across different topics for the same persona and
      confirm hashtag selection varies per post's actual content, not a
      fixed repeated set
- [ ] No external API calls (web search) introduced by this pipeline —
      confirm latency stays comparable to the existing writer/reviewer
      steps
